# ESP32 开发助手（esp32s3-bringup）作品说明

> 插上板子就知道它好不好、在干什么、出了问题该怎么办。
> 一个运行在 AI 编程工具（Velloc / Claude Code）里的 ESP32-S3 硬件助手插件。

## 1. 要解决的问题

拿到一块 ESP32-S3 开发板，新手和老手都会卡在同样的地方：

- 插上电脑没反应：是线不行、口不对，还是缺驱动？
- 板子到底是什么配置：Flash 多大、有没有 PSRAM、MAC 是多少？
- 程序跑起来了吗？Wi-Fi 连上没有？为什么一直重启？
- 串口 log 里一堆 `rst:0xc (RTC_SW_CPU_RST)`、`reason: 202`，看不懂。
- 想烧个固件，串口又被 monitor 占着；选错了 .bin，板子直接起不来。

这些问题平时要在设备管理器、esptool、串口工具、搜索引擎之间来回切换。本作品把它们收进**一个面板**，并且**用人话说明白**。

## 2. 作品亮点

### 2.0 AI 诊断：NVIDIA Nemotron（Nebius Token Factory）
- 每块板一个「🤖 AI 诊断」按钮；板子崩溃、反复重启、进入下载模式时它会成为高亮的主操作。
- 插件直接调用 **Nebius Token Factory** 上的 **NVIDIA Nemotron**（默认 `nvidia/Nemotron-3_5-Lightning`，可换 Nemotron Ultra），
  把芯片信息、运行摘要（状态、启动次数、复位原因、错误/警告数、Wi-Fi 状态）和最近 80 行串口日志交给模型，
  返回 **原因（引用证明它的那行日志）+ 最多 4 步修复建议 + 把握程度**，并在卡片上注明"由哪个模型分析、发送了什么"。
- 只在点按钮时发送；只用 Python 标准库，无额外依赖。

### 2.1 人性化设计
- **先说结论**：每块板顶部一句大白话结论（"程序运行正常 · 已运行 5 分 3 秒" / "程序崩溃了" / "板子刚重启：看门狗超时"），颜色一眼可辨（绿/黄/红）。
- **每个问题都附下一步**：串口被占用 → "关掉串口监视器后点「重试」"；烧录无响应 → "按住 BOOT，按一下 RST……"；找不到板子 → 三步排查清单。
- **术语翻译**：复位原因、Wi-Fi 断线原因码（201 → "找不到这个 Wi-Fi"，202 → "认证失败，密码可能不对"）、信号强度（-58 dBm → `▂▄▆·` 良好）。
- **不打扰**：芯片细节默认折叠；日志默认 30 行，可只看错误/警告或 Wi-Fi。
- **主操作突出**：当前最该点的按钮高亮（未识别时"识别芯片"，被占用时"重试"）。

### 2.2 安全可靠
- **只读优先**：扫描、识别、监视全部只读；唯一会写 Flash 的是烧录，且必须二次确认（面板确认卡片 / AI 必须先征得用户同意）。
- **防刷砖**：烧录前校验固件是给 ESP32-S3 编的**合并镜像**（魔数 0xE9、芯片 ID 9、0x8000 分区表），单独的 app/bootloader .bin、ELF、别的芯片固件一律拒绝。
- **不抢串口、不乱复位**：打开串口时不拉 DTR/RTS；端口被别的程序占用时不抢；检测/烧录自动暂停监视、完成后自动恢复并抓到新的启动日志。
- **烧录不怕中断**：进度百分比实时显示；进程意外终止会显示"烧录被中断，请重新烧录"，不会假装还在进行。

### 2.3 自动化
- 插上板子 2 秒内出现；识别过的板子按 USB 序列号记住，下次插上直接显示，不再复位。
- 确认是 ESP 的板子自动开始串口监视；拔线重插自动重连。
- 缺驱动时直接提示（Windows 错误码 28）并给出安装方法。

## 3. 功能一览

| 功能 | 面板 | 聊天 / 命令 |
|---|---|---|
| 发现板子、缺驱动提示 | 自动 | `/esp32s3-bringup:bringup` |
| 识别芯片（型号、Flash、PSRAM、MAC） | 「识别芯片」 | `probe` |
| 启动日志解读 | 监视区自动 | `/esp32s3-bringup:log` |
| 实时串口监视 + 状态/Wi-Fi 摘要 | 自动 | `monitor start/status` |
| **AI 诊断（NVIDIA Nemotron）** | 「🤖 AI 诊断」 | `explain` |
| 烧录合并固件 | `/esp32 flash <路径>` + 确认 | `/esp32s3-bringup:flash` |

## 4. 技术架构

```
Velloc 面板（JS mod）                       Python 脚本（pyserial + esptool）
┌───────────────────────────┐   进程调用   ┌───────────────────────────────┐
│ panel.js  轮询/动作/命令    │ ──────────▶ │ esp32_bringup.py  ports/probe/ │
│ core.js   板子与记录的合并  │             │   log/monitor/reset/flash      │
│ ux.js     结论/人话翻译     │ ◀── 文件 ── │ esp_monitor.py  监视进程、       │
│ view.js / monitor-view.js  │  (状态/日志/ │   摘要解析、烧录任务、镜像校验   │
│           纯函数渲染        │   烧录进度)  │                               │
└───────────────────────────┘             └───────────────────────────────┘
```

- **界面是纯函数**：同样的状态永远渲染出同样的界面，便于测试。
- **后台进程 + 文件协议**：监视进程独占串口，写日志和状态文件；面板只读文件；控制通过控制文件 + 确认应答，避免竞争。
- **适配宿主限制**：通过实验（spike）摸清 Velloc 的运行时边界（子进程随调用结束、无输入框、环境变量不可见），据此调整设计，而不是绕过限制。

## 5. 质量

- 单元测试：Python 103 个，JavaScript 130 个，覆盖解析、状态机、协议、界面渲染。
- 真机验证：ESP32-S3（QFN56, 16MB Flash, 8MB PSRAM, CP2102N）上实测识别、监视、复位、烧录（4MB，19 秒，校验通过）。
- 三轮独立代码审查（含一轮专门的界面体验审查），发现的严重问题全部带回归测试修复（如 Windows 文件替换竞争导致监视进程崩溃）。

## 6. 演示脚本（3 分钟）

1. 打开 Velloc，输入 `/esp32`：面板显示"还没发现板子"和排查清单。
2. 插上 ESP32-S3：2 秒内出现卡片，点「识别芯片」→ 显示 "16MB Flash · 8MB PSRAM · 240 MHz"。
3. 自动开始监视：结论"程序运行正常"，Wi-Fi 行显示信号条；点「复位」→ 看到启动日志，"上次重启原因：上电或按了复位"。
4. 点「错误/警告」筛选，展示红黄着色。
5. 输入 `/esp32 flash <固件>.merged.bin`：确认卡片显示大小、目标板、预计时间 → 确认 → 进度条走到 100% → 新固件启动日志。
6. 故意选一个 app-only 的 .bin：面板拒绝并解释"这不是合并好的固件"。
7. 在聊天里问 AI"板子为什么一直重启"：AI 调用同一套工具读日志并解释。

## 7. 已知限制

- 仅支持 Windows；烧录只支持合并好的单个 .bin。
- Velloc 面板没有输入框，烧录路径通过 `/esp32 flash` 命令给出。
- Wi-Fi 状态依赖 ESP-IDF 标准日志；Arduino 程序默认不打印 Wi-Fi 日志时显示"未知"。
